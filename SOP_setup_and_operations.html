Part 1 — First-time setup

This section replaces the previous SOP's setup instructions with full click-by-click detail — where to go, what to type, and where to find values (like the Project ID) the earlier version assumed you already had. It mirrors DEPLOYMENT_GUIDE.md in the package, with screenshots added. A handful of screens (the vRO wrapper's General tab, the Custom Resource form, the blueprint editor, and the Custom Form editor) are described in full text detail but aren't screenshotted in this pass — the lab UI became unresponsive partway through this capture session. Everything below still works from the text alone; ask for a follow-up pass to add the remaining images.

0. Logging in and finding your way around

Aria Automation bundles four sub-apps behind one login:

  • Assembler — build ABX actions, Custom Resources, and Cloud Templates. Most of this guide happens here.
  • Orchestrator ("vRO") — a separate app with its own JavaScript actions, used for the 15 wrapper scripts.
  • Service Broker — publish the finished template to a catalog, and where the Custom Form lives.
  • Pipelines — not used in this build.
  1. Go to https://<your-vra-host>/automation/. Log in with a Cloud Assembly Administrator account.
  2. You land on My Services with four tiles: Assembler, Orchestrator, Pipelines, Service Broker.
  3. Click a tile to enter that app. Each has its own top tab bar and a left sidebar that changes with the selected top tab.
Navigation tip: always reach a screen by clicking through tabs and the sidebar from the launcher, rather than pasting a deep-link URL into the address bar. Deep-linking occasionally leaves the app showing a stale page for the URL shown (a client-side routing quirk). If a page ever looks wrong, click a top tab away and back, or open a fresh tab from the launcher.

1. Finding or creating the Project, and finding the Project ID

  1. Assembler > Infrastructure tab > left sidebar, under Administration, Projects.
  1. To create one: + NEW, name it, add Administrators/Members on the Users tab, save. To use an existing one: click its card.
  2. Click OPEN on the project's card.
Where is the Project ID? It isn't printed as a labeled field on the Summary page. It's in the browser's address bar once the project is open — look for a long hyphenated hex string after /projects/edit/, e.g.: 
.../provisioning-ui;ash=%2Fprojects%2Fedit%2Fd347d2fd-4e27-4a0d-b144-f5262d7a70a1
Everything after edit/ is the Project ID. You'll need it for bootstrap/config.json.

2. Creating the 19 ABX Extensibility Actions

  1. Assembler > Extensibility tab > left sidebar > Actions.
  1. Click + NEW.
  1. Type the project name into Project — it autocompletes.
  1. Click NEXT. You land on the action editor: code on the left, settings on the right.
  1. Set runtime to Python 3.10 (or closest available). Delete the placeholder code, paste in the matching file from scripts_lab_raw/ (or scripts/f5_create_virtual_server.py).
  2. Main function: handler. Dependency: requests.
  3. Default inputs: leave empty for now (added in Section 4).
  4. SAVE, optionally TEST, then CLOSE and repeat for all 19 names (see DEPLOYMENT_GUIDE.md Section 2.2 for the full name list).
Record each action's ID from the browser URL as you save it (same trick as the Project ID) — you'll need all 19 in Section 5 to point the matching vRO wrapper at the right action. bootstrap/vra_bootstrap.py --apply can do this for you and writes the ID list to bootstrap/created_action_ids.json (unverified — see that folder's README).
Naming exception: the wrapper you build in Section 5 as f5_list_monitors should call the ABX action f5_list_monitors, not f5_list_monitor_types — see platform_config_raw/finding_monitor_type_vs_monitors.md for the full confirmed audit. f5_list_monitor_types.py itself is confirmed orphaned; safe to skip in a fresh build.

3. Default Inputs, Secret Inputs, and Action Constants

Do this after all 19 actions exist.

Needs f5_username + F5_SHARED_PASSWORDNeeds F5_VIP_SUBNET_REGISTRY (Action Constant)Needs F5_DEVICE_REGISTRY (Action Constant)
f5_create_virtual_server, f5_read_virtual_server, f5_delete_virtual_server, f5_update_pool_settings, f5_update_backend_nodes, f5_list_nodes, f5_list_nodes_grid, and every live-device f5_list_* actionf5_create_virtual_server onlyf5_list_clusters only
  1. Open the action > find Default inputs on the right panel (the same section shown empty in Fig. 6).
  2. Add a row: Type = Default, Name = f5_username, Value = the F5 API service account username.
  3. Add a row: Type = Secret, Name = F5_SHARED_PASSWORD. This opens/creates a vRA Secret rather than storing plaintext.
  4. Save. Repeat for every action in the left column above.

Action Constant #1: Extensibility > Actions > Action Constants sub-tab > + NEW > Name F5_VIP_SUBNET_REGISTRY, Value a JSON map of F5 host → VIP subnet CIDR (see DEPLOYMENT_GUIDE.md Section 4.3.1 for the exact JSON shape). Attach to f5_create_virtual_server.

Action Constant #2: same sub-tab > + NEW > Name F5_DEVICE_REGISTRY, Value a JSON map keyed by Location then Environment listing each F5 device's label and host (see DEPLOYMENT_GUIDE.md Section 4.3.2). Attach to f5_list_clusters. This is the actual F5 device inventory feeding the "F5 Cluster" dropdown — easy to miss since no wrapper or Custom Form field references it by name, but without it that dropdown silently returns zero options.

Known risk to raise with the client: one shared username/password is used for every F5 device. There's no per-cluster credential map today, despite a comment in f5_list_nodes.py referencing one — that pattern was never implemented. Flag this before go-live if the client has F5 clusters with different credentials.

4. vRO Orchestrator: the module and 15 wrapper actions

The Custom Form doesn't call ABX actions directly — it calls these 15 JavaScript "wrapper" actions in Orchestrator, which call the ABX actions above.

  1. From the launcher, click Orchestrator (a separate app, own left sidebar: Dashboard, Workflows, Actions, Configurations).
  2. Library > Actions > New Action. In Module, type com.f5.automation — typing it fresh and saving the first action creates the module automatically; there's no separate "create module" button.
  3. Name the first one f5_vra_run_action (create this first — every other wrapper except f5_generate_deployment_name calls it internally). Runtime: JavaScript. Paste in wrapper_scripts_raw/f5_vra_run_action.js.
  4. On the General tab, add the tag com.f5.automation (type it, press Enter). This is separate from the Module field — both are needed.
  5. Save, then repeat for the other 14 files in wrapper_scripts_raw/. Before saving each, replace its hardcoded ACTION_ID with the real ID you recorded in Section 2 for the matching ABX action.

Two Configuration Elements (create by hand)

  1. F5-Automation-Credentials (folder web-root) — attribute vraRefreshToken (SecureString): a long-lived vRA refresh token for a service account, obtained via POST /csp/gateway/am/api/login. Never write this value to a file.
  2. F5-Automation / DeploymentNaming — attribute sequenceCounters (Properties, empty): self-initializes on first use.

Verify: Library > Actions > filter Tags: com.f5.automation → 15 actions. Run f5_list_locations manually with no inputs as a smoke test.

5. Custom Resource, Blueprint, and Custom Form

Custom Resource (Design > Custom Resources > New): Resource Type Custom.F5.VirtualServer, paste the schema from platform_config_raw/custom_resource_F5.VirtualServer.md, wire lifecycle actions (Create/Update → f5_create_virtual_server, Read → f5_read_virtual_server, Destroy → f5_delete_virtual_server) and the three Day-2 actions, activate, scope to your project.

Blueprint (Design > Templates > New > Code editor): paste platform_config_raw/blueprint_F5-Virtual-Server.yaml, confirm every ${input.*} matches an inputs: entry, Test, publish a version.

Custom Form (Service Broker > Content & Policies > Content > expand the template's row > enable Custom Form): bind each field's External source to the matching vRO wrapper — full field-by-field table is in DEPLOYMENT_GUIDE.md Section 8. This screen wasn't screenshotted this round (lab UI was unresponsive) — worth a live check against the lab before finalizing the client's version.

Decide with the client whether to keep the blueprint's monitorType/monitorInterval/monitorTimeout inputs and the Custom Resource's pool.monitor_type field — they're not exercised by any live code path today (see finding_monitor_type_vs_monitors.md). Remove from both places together, or keep intentionally for a future "create new monitor" feature.

6. Publish and verify

  1. Service Broker > Content Sources > sync your project's content source.
  2. Content & Policies > Content > confirm Custom Request Form shows Enabled.
  3. Entitle the right project(s)/users.
  4. Submit one real test request end to end against a non-production F5 device — confirm cascading dropdowns, actual device changes, and all three Day-2 actions.
  5. Only then, move to Part 2 below with your operators.

Part 2 — Day-2 operations

For the deploying engineer using the published catalog item day to day.

1. Requesting a new virtual server

  1. Service Broker > Catalog > find the F5 Virtual Server item > Request.
  2. Fill the form top to bottom — each dropdown cascades from the ones above it (Location → Environment Type → F5 Cluster → everything else). If a dropdown is empty, the one above it hasn't been picked yet, or the vRO wrapper backing it is erroring — check Orchestrator > Activity > Action Runs for that wrapper's most recent run.
  3. Leave Virtual IP Address blank (or "auto") to auto-assign from the cluster's configured VIP subnet.
  4. Submit. Track progress under Assembler > Activity > Requests, or the deployment's own Events tab.

2. Updating health monitor / load balancing

  1. Open the deployed resource (Assembler > Resources, or from the original deployment).
  2. Resource actions menu > Update Health Monitor / Load Balancing.
  3. This only touches the pool's monitor and load-balancing method — it does not re-evaluate the virtual server, VIP, or existing pool members, so it's safe to run without risk of an "already exists" error on unrelated resources.

3. Updating backend nodes

  1. Resource actions menu > Update Backend Nodes / Pool Members.
  2. Add, remove, or change nodes in the grid. Every row needs a Port — a missing port fails the whole request with a clear error naming the offending node.

4. Resyncing from the F5 device

Resource actions menu > Resync from F5 Device — a read-only refresh of the resource's recorded state from what's actually configured on the device. Use this if the device was changed outside of this automation (directly on the F5, or via another tool) and vRA's record has drifted.

5. Deleting a virtual server

Deployment > Delete. This removes the virtual server for that deployment only — it leaves the shared pool and nodes untouched (they may be shared with other virtual servers on the same device).

6. Known risks and troubleshooting

  • Shared F5 credentials: one username/password for every F5 device (see Part 1, Section 3). If a request fails with an auth error against a specific device, confirm that device actually uses the shared credential set.
  • Health Monitor field: despite older naming, this field picks an existing monitor already configured on the device (via f5_list_monitors) — it does not create a new monitor type. See finding_monitor_type_vs_monitors.md.
  • A cascading dropdown is empty: check Orchestrator > Activity > Action Runs for the backing wrapper's most recent run and error message; also confirm the F5-Automation-Credentials Configuration Element's refresh token hasn't expired. If it's specifically the F5 Cluster dropdown, also confirm F5_DEVICE_REGISTRY (Section 3) is populated and still attached to f5_list_clusters — that's the one Action Constant this dropdown depends on.
  • Deployment Name sequence looks wrong: the counter lives in the F5-Automation / DeploymentNaming Configuration Element's sequenceCounters attribute — it's per Location + Environment Type, not global.
